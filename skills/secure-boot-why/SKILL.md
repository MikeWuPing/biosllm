# 是安全启动挡的，还是没轮到它

**安全启动拦的是镜像的签名，不是设备。** 一个 U 盘插着、能读、但不在启动
顺序里，症状和"被安全启动拒绝"一模一样：都是起不来。所以必须先分清这两类，
否则所有"U 盘启动不了"都会被错误地归到安全启动头上。

三层，按顺序过，**前一层不成立就不要看后一层**。

## 第一层：固件看见这个盘了吗

`dump_usb`，参数 `{}`

看 U 盘有没有被枚举出来：VID/PID、厂商/产品名、接口与端点。

- **没有 USB 设备** → 物理层面就没通。换口、换线、换机器，与安全启动无关。
  工具会区分"没有 USB 控制器"和"有控制器但没设备"，把这一句原样写进结论。
- **有设备但没有存储接口**（接口列表里没有 `Mass Storage`）→ 盘枚举了但不是
  可启动的存储设备（可能只是复合设备的一部分，或盘本身有问题）。
- **有 Mass Storage 接口** → 往下走。

`dump_disk`，参数 `{}` 补一件事：**容量对不对**。一个 32 GB 的盘报 8 MB，
说明分区表或介质有问题，这不是签名问题。

## 第二层：在启动顺序里吗

`read_env`，参数 `{"name":"Boot"}`

拿 `BootOrder` 和所有 `Boot####`。

1. `BootOrder` 里有没有指向 `Usb(...)` 的那一项？
   **没有** → 固件根本不会试它。这就是"插了 U 盘也没用"最常见的原因，
   与安全启动无关。结论要写成"不是盘坏了，是启动顺序里没有它"。
2. 有的话，看它的设备路径结尾是不是 `Usb(...)`，与 `dump_usb` 看到的设备
   对不对得上（同一台机器上可能插了多个 U 盘）。
3. `Boot####` 存在但 `BootOrder` 里没有它 → 这是一个"孤立的启动项"，
   固件不会尝试。需要把它加回顺序。

## 第三层：签名可不可信

只有前两层都成立（盘在、在启动顺序里、固件确实会试它），才轮到安全启动。

`dump_tpm`，参数 `{}`

看两个东西：`SecureBoot` 的值，以及 `db`/`dbx` 在不在。

| 状态 | 结论 |
|---|---|
| `SecureBoot = 0` | **安全启动没在拦**。问题在引导程序或文件系统，不要在签名上找原因 |
| `SecureBoot = 1`，`SetupMode = 0` | 正在执行。签名不在 `db` 里、或在 `dbx` 里的引导器会被拒绝——**这是当前最可能的原因** |
| `SecureBoot` 与 `SetupMode` 都是 1 | 固件状态自相矛盾，说清"不可信"，不要二选一 |
| `SecureBoot: absent` | 固件没实现安全启动，这一层可以整个跳过 |

**"最可能"不是"确定"。** biosllm 看不到镜像里的签名，也看不到 `db` 里的证书
内容，所以只能给出"这台机器在执行安全启动检查，而被拒绝的表现与此一致"。
要写成可能原因，并给出可验证的下一步。

## 怎么把"可能"变成"确定"

给用户两条可验证的路径，让他自己选：

1. **换一个已知签名的镜像**（原厂安装盘、微软官方介质）。能起 → 签名问题坐实。
2. **临时在固件里关掉安全启动**。能起 → 同样坐实，但要说清代价：
   关掉之后这台机器对任何引导器都不设防，装完要记得开回来。

**不要建议用户把自定义证书塞进 `db`** ——那需要动信任库，属于改机器状态，
不是诊断步骤，而且 `write_file` 这类工具改不了变量。

## 输出格式

### 盘被看见了吗
`dump_usb` 的结果，有没有 Mass Storage 接口；`dump_disk` 的容量是否合理。

### 固件会不会试它
`BootOrder` 里有没有对应项，路径是否匹配。

### 安全启动的状态
`SecureBoot`/`SetupMode` 的值，信任库是否非空。

### 结论
两三句：卡在哪一层、为什么这么判断、下一步做什么。

## 什么时候承认不知道

盘在、在启动顺序里、安全启动关着，但还是起不来 → 问题在引导程序本身
（`\EFI\BOOT\BOOTX64.EFI` 缺失、分区不是 FAT、镜像不完整）。**biosllm 看不到
文件系统里的内容**，直接说"这三层都正常，问题在引导程序或文件，需要另一套工具"，
不要硬编一个签名相关的理由。
